# 카페24 고객 데이터와 관리자 화면

## 구현과 경계

파이썬 VPS 상품도 Node 설치와 프로세스 운영이 가능하면 기존 Node 웹서비스와 PostgreSQL을 함께 사용할 수 있습니다. 기존 Python 서비스를 임의 교체하지 않습니다. 실제 상품에서 선택된 DB가 PostgreSQL인지 MariaDB인지 먼저 확인하세요. 이번 구현은 PostgreSQL용이며 MariaDB에 그대로 적용하면 안 됩니다.

- 클릭: 동의한 방문자의 지정 버튼만 날짜·버튼 ID·기기 크기별 합산. 이메일, IP, 쿠키 ID, URL, 자유 입력은 DB에 저장하지 않습니다. 클릭 수는 고유 고객 수가 아니며 자동화 요청/유실 가능성이 있는 참고 집계입니다. 메뉴 4종, 비교 담기, 시세 선택, 리포트 PDF/CSV/메일, 설문 저장을 계측합니다.
- 설문: 별도의 선택 동의와 저장 버튼을 누른 제출만 저장합니다. 자동 계산 기본값은 별도 실제 매출로 수집하지 않습니다. 이메일과 설문 답 전체를 AES-256-GCM으로 암호화하며 제출 ID로 암호문 바꿔치기를 검출합니다.
- 동의: 문구 버전, 제출 시각, 만료 시각을 기록합니다. 이메일 발송 동의와 DB 저장 동의는 별도입니다. 마케팅 수신 동의를 받은 것으로 처리하지 않습니다.
- 관리자: 기본은 서버의 `127.0.0.1:3102`에만 바인딩되며 SSH 터널 방식으로 접속합니다. 키는 브라우저 저장소에 쓰지 않고 탭 메모리만 사용하며 15분 후 화면을 잠급니다. 인증 키 자체는 회전 전까지 유효하므로 유출 시 즉시 교체해야 합니다.
- 표: 설문 최신 100건씩 다음 페이지, 현재 페이지 검색, 최근 30일 클릭 통계, 한 건 삭제. 이메일 기본 마스킹. 원문 표시를 켜면 CSV에도 원문이 포함됩니다. CSV는 검색 전 현재 페이지이며 전체 고객 일괄 다운로드 기능은 아닙니다. 다운로드한 파일은 별도 보호·삭제가 필요합니다.
- 감사: 조회/이메일 원문 보기/내보내기/삭제의 시각과 작업 종류를 기록합니다. 현재 단일 관리자 키 방식이므로 직원별 책임 추적은 없습니다. 다중 직원 운영 전 직원별 인증·MFA·권한 및 감사 주체를 추가해야 합니다.

## 서버 설정 순서

1. PostgreSQL DB와 전용 계정을 준비하고 DB 포트를 인터넷에 공개하지 않습니다. 같은 VPS의 loopback 연결을 사용합니다. 원격 DB는 `sslmode=verify-full`과 유효한 인증서가 필요합니다.
2. 스키마 소유자 계정으로 `deploy/customer-schema.sql`을 명시적으로 적용합니다. 앱 시작 시 자동 migration은 하지 않습니다. 기존 DB에 이 작업은 실행하지 않았습니다.
3. `npm ci`로 개발·테스트 의존성을 설치합니다. 운영 artifact에는 `npm ci --omit=dev`를 실행합니다. 운영 의존성은 `pg`, 테스트 의존성은 PostgreSQL WASM 검증용 PGlite입니다.
4. 환경변수에 DB URL, 서로 다른 무작위 32바이트 hex 암호화 키/관리자 키, 보유 일수(1~365), 회사명, 문의처, 동의 문구 버전을 설정합니다. 값은 채팅·GitHub에 올리지 않습니다. 회사 처리방침을 게시한 후 `CUSTOMER_DATA_ENABLED=true`로 켭니다. 어느 필수 설정이 빠져도 수집은 비활성입니다.
5. 웹 프로세스와 관리자 프로세스는 전용 비로그인 OS 계정으로 운영합니다. 관리자 프로세스 실행: `node --env-file=/안전한/관리자환경파일 server/customer-admin.js`. 공개 웹은 `node server.js`로 유지됩니다.
6. 기본(안전) 접속: 관리자 PC에서 `ssh -N -L 3102:127.0.0.1:3102 사용자@서버주소`로 터널을 열고 `http://127.0.0.1:3102`에 접속하세요.
7. 직원 공용 공개 접속(권장 고도화): `deploy/nginx-admin-public.example`로 `/admin` 서브도메인에 reverse proxy를 구성하고, 다음 환경변수를 추가하세요.
   - `CUSTOMER_ADMIN_PUBLIC=1`
   - `CUSTOMER_ADMIN_ALLOWED_HOSTS=admin.your-domain.example,127.0.0.1:3102`
   - `CUSTOMER_ADMIN_ALLOWED_ORIGINS=https://admin.your-domain.example`
   
   기본 키는 페이지 토큰 입력창에 넣습니다. 별도 employee OAuth/MFA/권한 분리는 후속 작업입니다. 공개 시에도 Node는 `127.0.0.1:3102`에만 바인딩하세요.
8. 운영자의 서비스 타이머/스케줄러에서 `node --env-file=/안전한/환경파일 scripts/customer-purge.mjs`를 매일 실행하도록 설치합니다. 설문 만료, 클릭 90일, 감사 365일 이후 삭제합니다. 조회는 만료 설문을 즉시 제외하지만 실제 디스크 삭제에는 purge 실행이 필요합니다. 스케줄러는 아직 설치하지 않았습니다.

DB 권한은 웹용(설문 INSERT, 클릭 INSERT/UPDATE)과 관리자용(조회·삭제·감사 기록), 스키마 소유자를 분리하세요. 각각 다른 프로세스 환경 파일의 CUSTOMER_DATABASE_URL을 사용합니다. 필요한 RETURNING/ON CONFLICT 동작에 대한 최소 SELECT 권한도 실제 DB에서 검증해야 합니다.

## 필수 운영 확인

실제 회사 DB 접속·마이그레이션, 실서버 TLS/방화벽, 백업 암호화·복원·삭제 반영, 키 백업·회전은 미실행입니다. 암호화 키 분실 시 기존 데이터를 복호화할 수 없습니다. 키만 즉시 교체하면 기존 암호문을 읽지 못하므로 재암호화 절차가 필요합니다. DB와 키가 함께 탈취되면 암호화만으로 보호되지 않습니다.

관리자용 DNS 주소를 쓰더라도 `0.0.0.0` 바인딩만으로 공개하지 마세요. Nginx Basic Auth + IP 제한 + HTTPS + (가능하면 직원 인증/MFA) 조합으로 보호해야 합니다.
직원별 로그인·MFA·권한 분리·감사 책임 추적은 현재 미구현입니다.
