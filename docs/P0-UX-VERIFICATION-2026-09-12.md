# MYSBIZON P0 개선 및 검증 보고서

- 작성일: 2026-09-12
- 작업 범위: P0 데이터 표현·순위·결측·손익 계산·개인정보 안내와 핵심 흐름 검증
- 검증 대상: 로컬 빌드 `http://127.0.0.1:3105/`
- 운영 반영: 하지 않음. 운영 사이트는 작업 전 릴리스 그대로 유지함

## 1. 수정 전후 흐름

### 수정 전

첫 방문에 서비스 소개 창이 검색을 가렸다. 지역을 고르지 않거나 특정 자치구를 고른 경우에도 비교 범위가 정확히 드러나지 않았고, 후보 목록의 번호와 실제 순위가 어긋나는 경우가 있었다. `예상 매출`, `한 곳당 매출`, `추천` 표현이 섞여 상권 집계값을 새 점포의 미래 매출처럼 받아들일 여지가 있었다.

손익 계산은 빈 입력에 기본값을 쓰면서 리포트에는 0원으로 적는 불일치가 있었고, 원가율 100% 이상을 95%로 바꿔 계산해 잘못된 본전값을 만들 수 있었다. 홈 안내는 이메일 외 정보를 수집하지 않는다고 읽혔지만 상세 안내에는 브라우저 저장·IP·접속 로그·선택 통계가 적혀 있어 서로 맞지 않았다.

### 수정 후

`업종·지역 선택 → 범위가 표시된 후보 결과 → 상세·지도 → 후보 2~3곳 비교 → 내 조건으로 손익 계산`이 한 상태를 공유한다. 지역을 고르지 않으면 `서울 전체`, 자치구를 고르면 그 자치구 안의 비교 가능한 상권만 다시 계산한다. 데이터가 없으면 임의 후보를 보여주지 않고 지원 범위와 다시 고를 방법을 안내한다.

매출 관련 핵심 표현을 `상권 참고 매출 (추정)` 또는 `점포당 참고 매출 (추정)`으로 통일했다. 이는 상권 소비액과 점포 수를 가공한 통계이며 새 가게의 예상 매출이 아니라는 설명을 결과·상세·비교·지도·리포트에 같은 뜻으로 표시한다.

후보 비교는 `저장한 후보 중`, `현재 선택한 기준에서`라는 범위를 함께 표시한다. 상권 소비 규모, 유동인구, 경쟁 점포, 점포당 참고 매출을 서로 다른 지표로 유지하며, 이번 검증에서 발견한 `상권 소비 규모`를 `손님 수`라고 부르던 문구도 바로잡았다.

손익 계산은 원가율 100% 이상이면 계산을 멈추고 수정할 값을 바로 알려준다. 빈 입력에 쓰는 기본값과 리포트 금액도 같은 계산 결과를 사용한다.

## 2. 실제 변경 파일과 이유

### 시작·결과·비교 흐름

- `frontend/app-logic.js`, `frontend/logic/screens.js`: 첫 방문 소개창 자동 표시를 없애고 기존 화면 상태를 유지한다.
- `frontend/logic/views.js`, `frontend/screens/42-find.html`: 서울 전체·자치구 비교 범위, 실제 표본 수와 순위, 자료 없음 상태, 점수 설명을 맞춘다.
- `frontend/logic/rank.js`: 점수의 비교 대상과 가중치 설명을 실제 계산에 맞춘다.
- `frontend/logic/comparison.js`, `frontend/screens/31-fine-compare.html`, `frontend/screens/40-zone-compare.html`: 저장 후보 1~3곳의 상태를 유지하고 비교 기준·기간·차이를 표시한다.
- `frontend/screens/41-region.html`: 상위 15개 업종이라는 제한이 해당 원자료 목록의 제한임을 분명히 한다.

### 숫자·지도·리포트

- `frontend/logic/util.js`, `frontend/logic/diagnosis.js`, `frontend/screens/43-diagnosis.html`: 손익 공식과 기본값을 한 곳에서 계산하고, 잘못된 원가율·비정상 숫자를 결과로 만들지 않는다.
- `frontend/logic/report.js`, `frontend/screens/45-sim.html`: 화면과 리포트가 같은 임대료·원가·고정비를 쓰며 계산 전제를 표시한다.
- `frontend/logic/analysis.js`, `frontend/logic/map.js`, `frontend/logic/chat.js`: 참고 매출·수요·경쟁의 뜻을 구분하고 지도 실패 시 상권 목록으로 계속 탐색하게 한다.

### 개인정보·언어

- `frontend/privacy.html`, `frontend/privacy.js`, `frontend/screens/02-overlay.html`: 서버의 `/api/config`를 읽어 이메일·고객 DB·클릭 통계의 실제 켜짐/꺼짐을 표시한다. 운영 주체·문의처·보유기간이 확정되지 않은 상태에서는 고객정보 저장을 켤 수 있다고 안내하지 않는다.
- `frontend/logic/i18n.js`, `frontend/locales/ko.json`, `frontend/locales/en.json`, `frontend/locales/zh-CN.json`: 바뀐 표현을 한국어·영어·중국어에 함께 반영한다.
- `frontend/screens/_shell-foot.html`, `frontend/company.css`, `api/config.js`: 하단 문의 이메일 영역을 별도 카드로 만들고, 실제 주소가 정해지면 `PUBLIC_CONTACT_EMAIL` 설정 하나로 안전하게 표시한다.
- `admin/admin.js`, `server/customer-admin.js`: 1차 Basic 인증과 2차 관리자 키가 같은 `Authorization` 헤더를 덮어쓰던 문제를 고쳐 2차 키를 전용 헤더로 분리한다.
- `tests/error-privacy.test.js`, `tests/ui-logic.test.js`: 개인정보 설정 일치, 후보 순위, 자치구 재계산, 원가율 100% 이상, 기본값 리포트 계산을 회귀 검사한다.
- `frontend/app.bundle.js`, `frontend/data.bundle.js`, `frontend/index.html`: 위 소스와 화면 조각에서 다시 생성한 배포용 결과물이다.

## 3. 계산 검증 사례

검증 화면은 `성수역 × 한식당`, 2026년 1분기 자료를 사용했다.

| 사례 | 입력·가정 | 기대 계산 | 실제 화면 |
| --- | --- | --- | --- |
| 기본 가정 | 임대료 400만원, 15평, 직원 2명×250만원, 기타 90만원, 원가율 35% | 고정비 990만원, 본전 `990 ÷ (1-0.35) = 1,523.08만원` | 본전 1,523만원 |
| 참고 매출 적용 | 상권 참고 매출 3,720만원, 원가율 35%, 고정비 990만원 | 영업이익 가정 `3,720×0.65-990 = 1,428만원` | 월 1,428만원 남음 |
| 잘못된 원가율 | 원가율 100% | 분모가 0이므로 계산 중단 | `계산할 수 없음`, `100% 미만으로 입력` |
| 시나리오 | 참고 매출의 70%·100%·130% | 매출과 이익만 변하고 같은 고정비의 본전선은 유지 | 세 시나리오 전환 시 일관되게 갱신 |

이 값은 세금·대출이자·개별 점포 임대료를 포함한 사업계획이 아니다. 공개 통계와 사용자가 넣은 비용으로 계산한 조건별 시뮬레이션이다.

## 5. 보안·개인정보 확인

공개 설정 API는 카카오 JavaScript 키와 기능 상태만 반환하며 서버 비밀키는 응답하지 않는다. 운영 라우터는 요청 본문 크기, 허용 메서드·콘텐츠 형식, Origin, 요청 수와 동시 요청 수를 제한한다. 관리자 API는 1차 Basic 인증과 2차 관리자 키를 검사하고, 2차 실패는 Basic 인증창을 다시 띄우지 않는 403으로 처리한다. CSV는 수식으로 실행될 수 있는 셀 앞에 안전 문자를 붙이며, 고객 저장 기능은 명시적 동의·암호화·만료 삭제 조건을 요구한다.

개인정보 안내는 개인정보보호위원회의 [2026 개인정보 처리방침 작성지침](https://www.privacy.go.kr/front/bbs/bbsView.do?bbsNo=BBSMSTR_000000000049&bbscttNo=20885)을 참고해 브라우저 저장, 서버 로그, 이메일, 고객 DB, 이용 통계를 구분했다. 운영 주체·문의처·실제 보유기간·외부 처리업체 계약은 회사에서 확정해야 하므로 임의로 작성하지 않았고, 그 전까지 관련 수집 기능은 꺼진 상태를 전제로 한다.

이번 점검은 코드 검토와 자동화된 회귀 시험이다. 침투 테스트나 보안 보증서는 아니며, 운영체제·Nginx·PostgreSQL 업데이트와 로그 감시는 서버 운영 절차로 계속 필요하다.

## 6. 테스트와 남은 제한

최종 명령:

```text
npm run build:html
npm run check:html
npm run check:data
npm test
npm run sums
npm run check:sums
```

최종 결과: 자동 테스트 69개 중 69개 통과, HTML 조각·배포 번들 일치, 10개 데이터 파일(상권 1,564곳·업종 62개) 구조 확인, Git 공백 오류 없음, 배포 파일 체크섬 일치.

남은 제한은 다음과 같다.

- 새 수정본은 운영 사이트에 배포하지 않았다. 운영 사이트는 기존 릴리스가 계속 서비스한다.
- 로컬에는 카카오 키를 넣지 않아 실제 지도 타일·핀 정보창 대신 실패 대체 흐름을 검증했다.
- 이메일 발송과 고객정보 저장은 꺼진 상태라 실제 외부 발송·운영 DB 입력을 실행하지 않았다.
- 운영 주체, 개인정보 문의처, 보유기간과 외부 처리업체가 확정되기 전에는 고객정보 수집을 켜면 안 된다.
- 390px·768px 자동 화면 크기에서는 가로 넘침을 확인했지만 실제 기기의 키보드·브라우저 조합과 예비 창업자 사용성 조사는 별도 검증이 필요하다.
- 임대료·공실은 모든 상권의 개별 점포 자료가 아니며, 현재 결과는 서울과 2026년 1분기 자료 범위에 한정된다.
- 광고는 P0 범위에서 추가하지 않았다. 콘텐츠·개인정보 동의·배치 기준을 확정한 다음 단계에서 검토한다.
