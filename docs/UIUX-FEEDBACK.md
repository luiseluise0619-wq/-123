# MYSBIZON UI/UX 및 자연스러운 데이터 확보 제안

2026-09-11. 실제 홈·검색·분석·리포트·인쇄 화면과 해당 코드를 확인한 피드백입니다. 사용자 인터뷰/행동 로그로 검증한 결과는 아니므로 개선 효과는 실험으로 확인해야 합니다. 후속 요청에 따라 상권 탐색·시세 선택·툴팁·반응형 선택 영역은 실제 반영했습니다. 아래의 리포트 질문 흐름과 데이터 수집 전략은 제안이며 아직 적용하지 않았습니다.

## 가장 먼저 바꿀 것

사용자가 결과를 본 뒤, 그 결과를 자기 상황에 맞추기 위해 다음 정보를 입력하게 만드세요. 현재 장점인 업종+선택 위치의 간단한 시작을 유지하고, 이후 리포트에서도 같은 원칙을 적용하는 것이 좋습니다.

현재 홈은 중앙 검색·큰 제목·민트 포인트로 충분히 정돈되어 있습니다. 반면 리포트는 지역·업종·창업 단계·나이·등록 여부·시기·지원 분야·비용·이메일로 최대 10단계를 거칩니다. 비용 질문은 화면 결과를 바로 보여주지 않고 PDF/메일에서 확인하게 되어 있습니다. 이번 키 미설정 실행에서는 지원사업을 제공하지 못하는데도 관련 질문을 거쳤습니다. 입력할 이유가 약해지는 부분입니다.

## 1. 데이터는 어떤 보상을 줄 때 물을 것인가

|사용자가 하는 일|물어볼 정보|바로 제공할 가치|입력 방식|
|---|---|---|---|
|첫 동네 탐색|업종, 관심 지역|관련 동네·구역 비교|현재 검색 유지, 위치 미정 허용|
|본전 결과 확인|월세|내 월세로 본전 결과 갱신|정확값 또는 모름, 단위 고정|
|인건비 조정|직접 운영 여부/직원 수|인건비 가정을 확인·수정|한 번 선택 후 결과 변화 표시|
|후보 비교|찜한 곳, 선호 이유|후보 차이 정리|클릭에서 얻은 선택과 선택적 이유|
|지원사업 탐색|준비/운영 단계, 등록 여부, 필요한 지원|맞는 공고 순서·해당 이유|기능 선택 후 조건부 질문|
|연령 조건이 있는 공고 탐색|해당하는 연령 구간|관련 조건 필터|생년월일 없이 필요한 구간만, 모름/건너뛰기|
|결과 저장|이메일|선택한 리포트 전송|결과를 본 뒤 선택적으로|
|다시 방문|계약/개업 여부, 바뀐 월세 등|이전 가정과 현재 조건 비교|이전 값 확인·수정, 선택적 응답|

추천 흐름은 `업종·지역 → 결과 → 월세 하나 보정 → 후보 비교/저장 → 원하는 사람만 지원사업 질문`입니다. 이미 알고 있는 업종·지역은 확인 가능한 칩으로 보여주고 다시 묻지 않습니다. 기존 상태 재사용은 유지하면서 무엇이 적용됐는지 더 명확하게 보이게 합니다.

질문 문구 예시:

- “월세를 알고 계신가요? 입력하면 이 결과를 내 조건으로 다시 계산해 드려요.”
- “직접 운영하실 예정인가요?” → 선택 후 필요한 직원 수 질문.
- “관심 있는 동네를 저장해 두면 다음에 이어서 비교할 수 있어요.”
- “이 리포트를 이메일로도 받을까요?” → 화면 보기/PDF와 별도로 선택.

실제로 제공하지 않는 혜택을 미리 약속하면 안 됩니다. 예를 들어 ‘상권 변화 알림’은 주기적 비교와 발송 기능이 생긴 다음 동의를 받습니다.

## 2. 현재 질문 흐름에서 고칠 구체적인 부분

1. **지원사업 준비 상태를 질문 전에 확인**: API가 미연결이면 손익 리포트를 바로 제공하고 지원사업 전용 질문은 접습니다. 다른 작업을 위한 입력에 쓰지 않는 나이를 먼저 받지 않습니다.
2. **창업 단계에 따른 분기**: ‘문 연 지 3년 넘었어요’라고 답한 사람에게 ‘언제 문을 열 계획이세요?’를 그대로 묻지 않습니다. 등록 여부는 단계에서 단정하지 말고 필요할 때만 확인합니다.
3. **진행률은 수행할 작업 기준**: 1/10만 보이기보다 ‘조건 확인 → 결과 → 저장’으로 목적을 보여주고, 세부 질문은 필요한 것만 펼칩니다. 예상 소요 시간은 실제 측정 후 표기합니다.
4. **입력과 결과를 가까이 배치**: 월세 입력 아래 본전 결과를 즉시 보여줘서 답변의 효과를 확인하게 합니다. 기본값과 직접 입력은 항상 구분합니다.
5. **이메일과 화면 열람 분리**: 현재 미리보기/PDF 경로가 있다는 장점을 더 명확하게 드러냅니다. 이메일 단계가 모든 결과를 보려면 필요한 관문처럼 느껴지지 않게 합니다.
6. **수정은 해당 항목만**: 완료 뒤 처음부터 재설문보다 ‘월세 수정’, ‘지역 변경’으로 바로 이동하도록 만듭니다.

관련 파일: `frontend/logic/report.js`, `frontend/screens/10-report.html`, `frontend/logic/storage.js`.

## 3. 더 편하고 깔끔하게 보이도록

### 홈

- 큰 제목과 간단한 검색은 유지합니다. 현재 검정 배경에서 검색칸·보조문구가 어둡게 보여 입력 영역의 대비를 높일 여지가 있습니다. 정식 대비 측정은 별도로 필요합니다.
- 전체 검정 대신 짙은 차콜과 한 단계 밝은 입력 면을 사용하는 안, 따뜻한 밝은 배경을 사용하는 안을 비교해 보세요. 기본 테마 변경 효과는 검증 전 단정하지 않습니다.
- ‘상권분석 / 정밀분석 / 통합시세’는 차이를 이미 아는 사용자에게 유리한 이름입니다. ‘동네 찾기 / 후보 비교 / 비용 알아보기’처럼 사용자의 행동으로 구분하는 안을 검토하되, 각 메뉴의 실제 기능 범위와 맞춰야 합니다.
- 현재 ‘인기 검색’ 세 항목은 실제 집계 근거가 없다면 ‘이렇게 검색해 보세요’로 표시하는 것이 맞습니다. 인기라는 표현은 집계를 구현한 뒤 사용합니다.
- 아래 빈 공간을 카드로 채우기보다 작은 실제 결과 예시 하나로 ‘검색하면 무엇이 나오는지’를 보여주세요. 처음 화면에서 기능 설명을 길게 늘리지 않습니다.

### 결과·분석

- 한 화면에서 가장 중요한 질문 하나를 먼저 답합니다. 예: “이 조건이면 월 얼마를 팔아야 본전인가요?”
- 핵심 수치 아래 `지역·업종·기간`과 `기본 가정 / 직접 입력 / 공공자료 기반 추정`을 붙입니다. 입력 수가 늘었다고 근거 없는 ‘정확도 95%’를 표시하지 않습니다.
- 주요 수치 1개 → 이유 2~3개 → 자세한 표/차트 순으로 위계를 만듭니다. 세부 자료는 접되 주요 가정과 한계는 숫자 가까이 남깁니다.
- 민트는 주된 다음 행동과 선택 상태에 집중합니다. 모든 지표·카드·아이콘을 강조하면 무엇을 볼지 다시 고민하게 됩니다.
- 금액은 오른쪽 정렬하고 `월`, `만원`, 기준 시점을 반복 없이 명확하게 표시합니다. 통일된 카드 간격·모서리·버튼 높이를 적용합니다.
- 목표 사양 예시: 본문 16px 안팎, 주요 버튼 높이 44~48px 이상, 8/16/24/32px 간격 단계. 사용자 기기·확대·한글 줄바꿈으로 검증합니다.

### 리포트

- 인쇄용 페이지는 이미 밝은 문서형 구성이 안정적입니다. 다만 화면 열람에서는 핵심 결과가 본문 설명과 표 아래로 밀립니다. 첫 부분에 본전 값·주요 조건을 두고 산출 근거 표를 아래에 유지하는 안이 좋습니다.
- 이번 예시처럼 구만 고르면 그 구의 대표 상권으로 계산되는 경우, 결과를 보여주기 전에 ‘홍대소상공인상점가 기준으로 보기 / 직접 고르기’를 명확하게 제시합니다. 현재 있는 설명을 더 눈에 띄게 만드는 것입니다.
- ‘함께 본 자리’가 사용자가 실제 선택한 후보인지 추천 후보인지 표시를 맞춥니다. 이번 리포트에는 선택 지역 밖 후보도 포함됐으므로 추천 범위도 보여주는 편이 좋습니다.
- 준비 중 기능은 클릭 후 막히게 두기보다 진입점에서 상태와 가능한 대안을 보여줍니다. 지도 준비 상태에서도 목록 비교는 이어갈 수 있어야 합니다.

### 모바일·접근성

- 입력은 한 열로 정리하고 모바일 키보드가 결과/다음 버튼을 가리지 않게 합니다.
- 펼침·자동 다음 질문 시 포커스와 스크롤 위치가 자연스럽게 이동하는지 확인합니다. 이전 답을 바꿀 수 있는 경로를 유지합니다.
- 아이콘만 있는 설정, 작은 보조글, 색만 다른 증감 표시를 점검합니다. 키보드·스크린리더 동작은 시각적으로 예쁜 것과 별도로 검증해야 합니다.

## 4. 우리에게 실제로 쌓이는 데이터로 만들려면

현재 코드에서 설문은 주로 sessionStorage, 일부 선택은 localStorage에 저장됩니다. report API는 내용을 메일로 전달하며 중앙 설문 데이터베이스가 아닙니다. 사용자가 많이 입력해도 제품팀의 분석 데이터가 자동으로 쌓이는 구조는 아닙니다.

따라서 UI 질문 추가와 별도로 데이터 목적을 나눠 설계해야 합니다.

|목적|최소 기록 예시|구분할 것|
|---|---|---|
|UX 개선|검색 완료, 결과 표시, 질문 노출/답변/건너뛰기, 저장 완료|입력 원문과 이메일은 일반 이벤트에서 제외|
|개인화|사용자가 저장하기로 한 업종·후보·가게 조건|기기 임시 상태와 서버 저장 상태|
|시장 정보 보완|사용자가 별도 제공한 월세 등, 관측 시점·지역 단위|희망값/견적/계약값/기본값/추정값|
|재방문 성과|선택적 개업·계약 여부 업데이트|의향과 실제 행동, 자기보고와 확인된 사실|

기본값 400만원을 사용자가 입력한 실제 월세로 집계하면 안 됩니다. 조절해 본 값도 확정된 예산이나 실적이 아닙니다. 예비창업자/운영자/단순 탐색자를 구분하고, 응답 시점과 출처·질문 버전·값의 상태를 함께 저장해야 후속 분석에 쓸 수 있습니다. 개인화용 입력을 시장 벤치마크로 재사용하려면 그 목적을 별도로 설명하고 선택을 받는 설계가 적절합니다.

‘모름’과 ‘건너뜀’은 0으로 저장하지 않습니다. 범위 입력은 대표값을 실제값으로 둔갑시키지 않고 범위 그대로 보관합니다. 검증되지 않은 사용자 제보는 공공자료와 분리하고 소수 표본을 지역 대표 통계로 표시하지 않습니다. 수정/철회 경로, 보존 기간, 중복·이상 입력 검증도 데이터 기능에 포함해야 합니다.

이메일 전달 동의, 알림 신청, 제품 분석·시장 데이터 활용은 사용자가 각각 이해할 수 있게 구분합니다. 전환율을 높이려고 필수처럼 보이게 만들거나 기본 체크로 묶지 않습니다.

## 5. 효과를 어떻게 검증할 것인가

첫 실험은 ‘현재 리포트 흐름’과 ‘결과 먼저 + 비용 질문 1개’의 비교로 충분합니다. 화면 전체 색·메뉴·설문을 한꺼번에 바꾸면 원인을 파악하기 어렵습니다.

- 주지표: **실제로 결과를 본 사용자 중, 유효한 자기 조건을 자발적으로 제공한 비율**.
- 함께 볼 지표: 첫 결과까지 걸린 시간, 검색→결과 도달률, 질문별 이탈/건너뛰기, 기본값에서 수정한 비율, 결과 저장 성공률.
- 품질 지표: 기본값을 제외한 유효 응답률, 모순/이상값 비율, 재방문 수정률. 이메일 수만 목표로 두지 않습니다.
- 악화 방지: 결과 열람 완료율, 오류율, 철회/불편 신고가 나빠지지 않는지 봅니다.
- 예비/운영 사용자와 신규/재방문을 분리하고 실제 트래픽 규모에 맞는 표본·기간을 정합니다. 지금은 트래픽 정보가 없어 증가율을 예측할 근거가 없습니다.

우선순위는 **① 결과 먼저·지원사업 질문 분기 ② 입력 즉시 결과 갱신 ③ 상태 재사용·선택 저장 ④ 대비·간격·정보 위계 정리 ⑤ 목적이 분리된 서버 저장·분석**입니다. 장기적으로 시장 데이터를 활용할 계획이라면 저장 스키마와 목적 설명은 수집 기능 출시 전에 먼저 정해야 합니다.

## 후속 요청 반영: PC·태블릿·모바일 UI

- 상권 비교: 구별 전체 목록, 이름 검색, 12개씩 더 보기, 선택 상태 표시, 최대 3곳 비교. 다른 구로 이동해도 담은 상권이 유지됩니다.
- 목록은 PC 3열(1100px 이상), 태블릿 2열(600~1099px), 모바일 1열입니다. 선택 메뉴는 높이 48px이며 화면 폭에 맞춰 배치됩니다. 1440×900, 820×1100, 390×844에서 브라우저 확인했습니다. 실물 모든 기기 검증은 아닙니다.
- 통합시세: 임대료/공실률은 조사 권역·상권, 소비지출은 구, 매출/개폐업 등은 업종 선택을 제공합니다. 데이터가 없는 구×업종 시계열을 만들어내지 않습니다.
- 차트 툴팁: 표시 애니메이션 제거, 가로 막대의 y축 선택, 테마에 맞는 글자 대비 수정. 코드 회귀 검사와 브라우저 툴팁 표시를 확인했습니다. 실제 hover-only 지연 시간은 계측하지 않았습니다.
- 토스·애플을 참고한 여백, 간결한 라벨, 정돈된 선택 카드 스타일을 새 선택 영역에 적용했습니다. 사이트 전체 디자인 교체는 아닙니다.
- 프런트 계산/원천 데이터와 vendor는 보존했습니다. CSS·화면 조각·언어 사전·생성 index는 사용자 후속 요청으로 변경했습니다. index는 빌드로만 생성했습니다.
- 데이터 수집의 단계적 질문 설계는 docs/UIUX-FEEDBACK.md, 회사 계정 이전과 추가 API는 deploy/API-MIGRATION.md에 정리했습니다. 실제 회사 계정 이전·사용자 정보 수집 서버 추가는 수행하지 않았습니다.
